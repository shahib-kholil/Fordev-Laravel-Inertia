# Unauthenticated Django DEBUG pages disclose application internals

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-09-04 07:40:56 UTC
**Target:** https://alfikr.id/
**Endpoint:** /save-token/; /data/json/berita/; arbitrary invalid paths
**Method:** GET
**CWE:** CWE-209
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Trivial

## Description

Unauthenticated requests can trigger Django technical error pages that disclose restricted application configuration and source details. The pages expose framework/runtime versions, traceback and filesystem paths, route configuration, and backend connection metadata, materially aiding targeted attacks even though secret and password values are masked.

## Evidence

Unauthenticated technical 500 response from `/save-token/`:

```text
HTTP/1.1 500 Internal Server Error
Exception Type: JSONDecodeError
Exception Location: /usr/local/lib/python3.12/json/decoder.py
Raised during: berita.views.save_token
DEBUG = True
BASE_DIR: PosixPath('/home/web2')
DATABASES: mysql, HOST: localhost, NAME: alfikr_news_v2, USER: alfikrco
EMAIL_HOST_USER: alfikrdotco@gmail.com
MEDIA_ROOT: /home/web2/media
STATIC_ROOT: /home/web2/staticfiles
```

The same response contains installed applications, middleware, request metadata, and full traceback/source snippets. `/data/json/berita/` independently returns HTTP 500 with `AttributeError` at `/home/web2/berita/views.py` line 1341. A random invalid path returns a DEBUG 404 stating `DEBUG = True` and listing the URLconf routes, including `admin/alfikr/`, `redaksi/`, data, management, and media paths. `SECRET_KEY`, database password, and SMTP password fields render as `********************`; no raw secret was observed.

## Impact

An Internet attacker can enumerate internal URL routes and learn deployment paths, framework versions, database/SMTP identities, middleware, installed applications, and storage locations without authentication. This information lowers the cost of targeting additional vulnerabilities; no raw signing key or password was obtained during validation.

## Counterevidence

Django's `SafeExceptionReporterFilter` masked `SECRET_KEY`, database password, SMTP password, and other sensitive setting values, and the tested administrative login path did not expose an unauthenticated admin interface. Nevertheless, the debug setting, complete tracebacks, source paths, route inventory, runtime versions, and connection identities remained visible on multiple unauthenticated routes, so the information disclosure is not eliminated.

## Confidence Rationale

A working unauthenticated proof of concept was independently reproduced against the live service on multiple deterministic routes and a random invalid path.

## What Would Change This Severity

Discovery of an unmasked signing key, database/SMTP credential, or other credential in the same pages would raise the severity to high or critical; confirmation that all disclosed values are intentionally public would lower it.

## Technical Analysis

Django is deployed with `DEBUG = True` on the public service. A malformed unauthenticated request to `/save-token/` raises `JSONDecodeError` because the handler parses an empty GET body, while `/data/json/berita/` raises an `AttributeError`; both responses are full Django technical 500 pages. The technical pages include traceback frames and source snippets, `/home/web2/berita/views.py` and `/home/web2/alfikr_env` paths, Django/Python versions, `BASE_DIR`, database and SMTP metadata, `MEDIA_ROOT`/static paths, installed applications, middleware, and request metadata. A random nonexistent path returns a DEBUG 404 with the complete URLconf route inventory, including administrative and data-management routes. Django's exception filter masks `SECRET_KEY` and password fields, but the remaining disclosure is still restricted operational information.

## Proof of Concept

1. Send an unauthenticated `GET` request to `/save-token/` without a request body.
2. Confirm the server returns HTTP `500` with a Django technical error page containing `DEBUG = True`, the `JSONDecodeError` traceback, source paths, runtime versions, settings metadata, and request information.
3. Send an unauthenticated `GET` request to `/data/json/berita/` and confirm a second technical `500` page with an application traceback and the same settings disclosure.
4. Request a random nonexistent path and confirm the DEBUG `404` page lists the application's URLconf routes, including `/admin/alfikr/` and management/data endpoints.
5. Verify that the displayed `SECRET_KEY` and password values are masked, while the other configuration and source metadata remains visible.

```python
import requests

base = "https://alfikr.id"
paths = ["/save-token/", "/data/json/berita/", "/debug-route-does-not-exist"]
markers = [
    "DEBUG = True",
    "Traceback",
    "Exception Type",
    "Installed Applications",
    "DATABASES",
    "BASE_DIR",
    "Alfikr.urls",
]

for path in paths:
    response = requests.get(base + path, timeout=20, allow_redirects=False)
    body = response.text
    print(path, response.status_code, len(response.content))
    print({marker: marker in body for marker in markers})
    print("secret_masked", "********************" in body)
```

## Remediation

Set Django `DEBUG = False` in every production deployment and enforce the setting through deployment configuration rather than a developer default. Configure a generic production error handler and ensure unhandled exceptions are logged only to access-controlled monitoring. Review all public routes for unauthenticated exceptions, add regression tests that malformed requests receive generic responses, and restrict administrative and management endpoints behind authentication and authorization. Rotate any credentials if future review finds them exposed in unmasked diagnostics.

## Assumptions

The service is Internet reachable as observed and the attacker requires no authentication or victim interaction. The impact assessment assumes the disclosed database and SMTP identities are not themselves credentials; no unmasked secret was demonstrated.
